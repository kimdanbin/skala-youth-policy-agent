# 청년정책 안내 에이전트 — 설계 문서 (Step 5 기준)

## 1. 구조

```
        ┌──────── supervisor (계획: LLM + 코드 보정) ────────┐
        │        │                 │                │
      chat    clarify        policy_agent       doc_agent      ← both면 두 서브에이전트를 동시에 실행
        │        │           (MCP Tool)          (RAG + LLM 채점·재검색)
       END      END                └──────┬─────────┘
                                       review ── 부족 → 재계획(LLM) → 실패한 서브에이전트만 다시 (최대 1회)
                                          │ 충분 / 한도 도달
                                        write (MCP Prompt로 답변 규칙 받아 LLM 작성) → END
```

| 가이드 항목 | 구현 위치 |
|---|---|
| Supervisor 패턴 | `backend/agent/supervisor.py` plan_node / review_node |
| 전문 서브에이전트 분리 | `policy_agent.py`(MCP 도구), `doc_agent.py`(RAG) |
| 동적 재계획 | review_node: 결과가 부족하면 LLM이 계획 수정 → 실패한 쪽만 재실행 |
| MCP Tool / Resource / Prompt | `mcp_server/server.py`: 도구 4개, `policy://catalog`, `policy_answer_prompt` |
| RAG | `backend/rag/` (bge-m3 + Chroma, 문서 필터 `program`) |
| 의존성 주입 | `backend/agent/deps.py` (진짜/가짜 부품 교체), `FAKE_TODAY` 날짜 주입 |
| 단위 테스트 | `mcp_server/test_tools.py`(9개), `backend/tests/test_agent.py`(25개) |

설계 선택: **계획·평가·재계획은 LLM, 도구 실행은 코드** (Anthropic "Building effective agents"의
orchestrator-workers + evaluator-optimizer 패턴). 로컬 소형 모델에서도 안정적이고 평가 재현성이 높다.
대가: 정해진 흐름 밖의 질문에는 유연하지 않다 → 향후 정책조회를 LLM 도구 선택(ReAct)으로 바꿔 비교 가능.

## 2. 노드끼리 주고받는 데이터 (state.py)

- `Plan`: route(chat/clarify/policy/doc/both), birth_year/month/day, age, region, keyword, category(분야 19개 중), doc_query, doc_program(청년정책집/청년월세/청년내일저축계좌)
- `Grade`: enough, reason, better_query
- `AgentState`: question, plan, plan_source(llm/fallback), age, region_info, policy_result, doc_result, replan_count, next_agents, answer, sources, path·llm_calls·notes(동시 실행 대비 이어 붙이기 reducer)

## 3. 무한 반복·오류 방어

| 방어 | 값 |
|---|---|
| 문서 재검색 | 최대 2회 (검색 최대 3번) |
| 재계획 | 최대 1회 |
| 그래프 전체 단계 | recursion_limit 25 |
| 질문 하나 시간 | 300초 초과 시 안내 문구 |
| 모든 예외 | `run()`이 잡아서 안내 문구 + error 기록 (내부 오류 노출 안 함) |

질문 하나당 LLM 호출: 보통 3~5회, 최대 1(계획)+3(채점)+1(재계획)+3(채점)+1(답변) = 9회. 단순 RAG(Before)는 1회.

## 4. 검증하면서 고친 것 (데이터 전수 확인으로 발견)

1. **지역 판단을 기관 이름 → zipCd(시군구 코드)로 변경.** 이름 기준이면 `region="전주"`에 전주시 정책 13개가 0개 나왔다(전부 "전북특별자치도"로 저장). 기관명이 부서명뿐인 정책 110개는 지역을 알 수 없었다. zipCd는 3,472개 전부 있다.
   - 시군구 코드 표는 데이터에서 만든다(127개). 표에 없는 도시(예: 수원)는 도 단위로 넓혀 찾고 그 사실을 표시한다.
   - 이 데이터는 광주·전남이 "전남광주통합특별시"로 합쳐져 같은 앞자리(12)를 쓴다 → 광주 5개 구 코드로 구분.
   - 중앙부처 정책이라도 코드가 14개뿐인 지역 한정 정책이 있다 → "전국" 여부도 코드 수(200개 이상)로 판단.
2. **나이 범위**: 생년만 알면 23~24세처럼 범위 → 범위 안 나이 중 하나라도 맞으면 포함 (큰 값만 쓰면 최대 23세 정책이 빠짐).
3. **정렬**: 키워드가 정책 이름에 있는 것 우선('월세'가 '전월세 및 주거급여 지원' 분야에 걸려 신혼부부 전세대출이 앞에 오던 문제), 지역을 모르면 전국 정책 우선, 같은 이름 중복 등록 제거.
4. **FAKE_TODAY가 MCP 서버 프로세스로 전달되지 않던 문제**: 환경변수를 명시적으로 넘기도록 수정 (`mcp_tools.py`, `try_mcp.py`).
5. **모르는 지역**은 조용히 무시하지 않고 오류 → 에이전트가 받아서 "지역 인식 못함" 기록 후 지역 없이 진행.

## 6. 실제 모델(qwen3:8b, 맥 로컬) 실행 결과 — 2026-10-21

### 1차 실행에서 드러난 문제와 수정 (모두 테스트로 고정)

| 실측 문제 | 원인 | 수정 |
|---|---|---|
| "서울 사는데", "전주 사는데"인데 지역이 비어 전국 결과 | qwen3가 region 칸을 자주 비움 | LLM이 비우면 질문 글에서 지역을 직접 찾음 |
| 키워드 없이 첫 조회 → 1,078개 전체가 결과 | 계획에 keyword가 없으면 '키워드 없음' 조회가 먼저 나감 | 키워드 없는 조회는 마지막 수단으로 |
| '월세' 질문에 신혼부부 전세대출 | keyword를 비우고 분야(전월세 및 주거급여 지원)로만 찾음 | 질문의 낱말로 키워드 보충 |
| "내일배움카드로 뭘 배워?"를 정책 목록으로만 처리 | qwen3가 route=policy 선택 | 제도 내용 질문이면 문서검색 포함(both)으로 보정 |
| 문서 채점이 계속 '부족' → 재계획까지 해서 LLM 9회·115초 | 개인 자격 판단까지 요구하는 채점 기준 + 문서는 보조 자료인데도 재계획 | 채점은 '찾을 정보' 기준, both에서 정책을 찾았으면 문서 때문에 재계획하지 않음, both의 문서 재검색은 1회까지 |
| 문서에서 온 제도에 '모집 끝났어요'를 지어냄 / 다른 정책의 기준을 옮겨 씀 | 답변 규칙이 신청 상태 출처를 구분하지 않음 | MCP Prompt 규칙 3·2 보강 |
